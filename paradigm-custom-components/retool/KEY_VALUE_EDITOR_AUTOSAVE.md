# Nonblocking KeyValueEditor saves

The updated editor keeps its inputs enabled while a save request runs. Every edit immediately updates a local draft; valid changes are batched after a quiet period. At most one save request is in flight. When its acknowledgment arrives, the editor advances the saved baseline and retains all newer edits, then submits the next batch when its idle delay has elapsed.

## Inspector settings

| Field              | Value                                                                                                       |
| ------------------ | ----------------------------------------------------------------------------------------------------------- |
| `autoSave`         | `true`                                                                                                      |
| `typingDebounceMs` | `2500` is a reasonable starting point; this now measures a typing pause, not a period of disabled inputs    |
| `debounceMs`       | `900` or `1000` for dropdowns/checkboxes                                                                    |
| `saveWhileFocused` | `true` to save on idle while focus stays in a field; `false` to wait for that field to lose focus           |
| `disabled`         | `false`, unless the entire record is intentionally read-only; do not bind it to a save query's `isFetching` |
| `saveResult`       | `{{ measureEditorSaveResult.value }}`                                                                       |

No input is disabled just because the component's `isSaving` output is true. Read-only fields and explicit `disabled` settings are still respected. Discard is unavailable while the current record's request may be committing. Save can queue additional edits during an in-flight request; autosave performs the same follow-up automatically.

## Blue spinners on native Retool cards

The November 4 14:44 recording shows blue loading circles on the native summary cards above the editor during background refreshes; these are not generated by KeyValueEditor. In the inspected app export, `measuresGridView.data` binds directly to `qSelectedMeasureOverview.data`, and app-level `loadingIndicatorsDisabled` is false. The save handler refreshes the overview and details queries after each saved batch, so native query-dependent widgets can repeatedly show loading states even while the editor stays usable.

To suppress those automatic indicators, open **App settings → General → Show loading state** and turn it off. This is an app-level setting, so it affects automatic loading indicators elsewhere too. It does not stop queries, skip saves, or remove the editor's own Saving/Saved/error text. [Retool loading-state discussion](https://community.retool.com/t/loading-field-circle-on-components-no-longer-works/62611).

If loading indicators must remain elsewhere, isolate the summary cards from the query's fetching state using a temporary-state cache: populate it on project load and successful refresh, and bind `measuresGridView` to that state rather than directly to the running query. That requires host-app binding/event changes; do not simply remove refreshes, because the summaries would become stale. The app setting and these host bindings have not been changed by the component deployment.

## Existing Retool handler

Keep using the **save** event and the immutable `customMeasureDetails.saveRequest` snapshot. Do not read `customMeasureDetails.value` or `changeset` halfway through a request: they now continue changing as the user types. [measureDetailsSaveHandler.js](measureDetailsSaveHandler.js) already uses the snapshot and returns a matching acknowledgment:

```js
await measureEditorSaveResult.setValue({
  requestId,
  success: true,
  persistedValue, // the actual row returned by SQL / refreshed details
});
```

On failure, acknowledge `{requestId, success:false, error}`. A matching acknowledgment is essential; without it, the editor retains its draft and waits without starting overlapping requests.

The latest handler's `persistedValue` is supported: trigger-normalized values are adopted for fields the user has not edited again. Newer edits win even if the user changed a field back to its old value or back to the submitted value during the save. If a returned row omits a submitted field, that change stays unsaved and automatic retries pause instead of falsely reporting it saved. Older handlers that return only `{requestId,success:true}` still work by treating the submitted snapshot as saved, but cannot reflect database-normalized values.

After a failed save, the latest draft remains available. Another edit or explicit Save retries it; failures are not retried forever in the background. Invalid intermediate JSON, numbers or dates prevent that record's next batch from being submitted until corrected.

## Record selection and cache lifetime

Drafts are cached per record **in memory for the mounted component session**. Switching records does not erase the old draft, and a late acknowledgment only updates its original record. Only the selected record automatically starts new save requests; a cached unsaved draft resumes when that record is selected again. Other retained drafts are indicated in the header. This is not persistent storage across page reloads, closing the app, unmounting the component, or changing library versions.

New outputs:

- `isSaving`: a save request is awaiting its acknowledgment.
- `hasUnsavedChanges`: any cached draft is unsaved or a request is in flight.
- `isDirty`: the selected record differs from its last saved baseline (existing output).

For the existing measure editor, disable **record/project navigation**, not the editor inputs, while `{{ customMeasureDetails.isSaving || customMeasureDetails.isDirty }}` is true. Its downstream Outlook/calendar success scripts may still use the selected measure; this guard keeps that context stable until the selected record's queue drains. If navigation bypasses the guard, a clean current record can still navigate back to another cached draft and resume its saves. `hasUnsavedChanges` can be used for an overall unsaved-work indicator. Cached drafts do not make external scripts that use the current selection safe for background records. The save handler's own database writes already target the captured record ID.

## Validation

Automated tests cover batching/idle timing, keeping inputs enabled during saves, sequential requests, edits/reverts during a request, authoritative database values, missing-field acknowledgments, failed saves, stale responses, query refreshes, record selection changes, manual queues, invalid inputs, status-clearing rules, and the existing Retool handler contract. Verify the full Retool/database/Outlook path in dev before promoting a numbered library release.
